TOPIC: prior-art-wiiu
----------------------------------------------------------------------------------------------------
SUMMARY:
Prior art on Wii U media/streaming homebrew is thin but directly relevant, and the receiver niche is empty. The strongest proof-of-concept for WiiU Cast's core pipeline is Moonlight Wii U (GaryOderNichts): it demonstrates network -> Wii U hardware H264 decode -> GX2 display end-to-end. Its src/wiiu/decode.c uses the native H264DEC API (H264DECOpen/Begin/SetBitstream/Execute), outputs NV12 semi-planar frames into GX2 textures (R8 Y-plane + R8G8 UV-plane), sizes buffers for up to 2800x1408 pitch and references H.264 level 4.2. Community-reported performance: 720p@60fps "almost flawless" with the LAN adapter; issue tracker shows Wi-Fi instability above ~5000 Kbps bitrate, disconnects, and reconnect bugs — a key data point for casting high-bitrate files over Wi-Fi. Repo is GPL-3.0, active (pushed 2026-02-14), last binary release v1.6 (Feb 2024). The closest thing to a modern local media player is CaféMP (whateveritwas/cafemp), created April 2025 and still actively developed (pushed 2026-08-05): FFmpeg demux + attempts hardware decode via avcodec_find_decoder_by_name("h264_wiiu") with software fallback, SDL2 audio, Dear ImGui/GX2 UI, PTS-based A/V sync with audio master clock, 4-thread architecture, DMAE GPU copies, .wuhb packaging. It targets only 720p30 ("goal, not a guarantee") and its issues log console-crashing bugs (360p panic, seek freezes, memory assertion crashes). Critically, its roadmap lists DLNA/Jellyfin streaming as planned but no network code exists in the tree — so it is a would-be streaming CLIENT (pull), not a cast RECEIVER (push). No Wii U homebrew acting as a DLNA/UPnP renderer, AirPlay, Chromecast, or Miracast receiver was found anywhere (GitHub search, web search, hb-appstore repo.json) — the WiiU Cast premise appears novel on this console. The seed lead "Ristretto" is NOT a video player: it is an Aroma plugin running an HTTP server (port 8572) for smart-home/IoT control (wiiu-smarthome org), valuable as prior art for an always-on HTTP endpoint on Aroma and for its documented gotcha that the server dies when the Home menu/applets are open. Kodi/VLC were never ported (GBAtemp consensus: infeasible/abandoned ideas). Supporting pieces: GaryOderNichts/FFmpeg-wiiu (FFmpeg fork adding the h264_wiiu hardware decoder, stale since Dec 2020), VLCu (WIP, unusable, MIT), sdl-ffmpeg-player-wiiu (2018 software-decode experiment), WiiMC (vWii/Wii-mode only, not Cafe OS), and the historical practice of streaming to the stock browser via VLC HTTP (AAC-only audio worked). wut ships the full H264DEC API in include/h264/decode.h but documents no hard profile/level/resolution limits — those must come from Moonlight's empirical values or hardware testing.

TOPIC: prior-art-cross
----------------------------------------------------------------------------------------------------
SUMMARY:
Architecture-to-copy is well established: a UPnP/DLNA MediaRenderer is SSDP (UDP multicast 239.255.255.250:1900 NOTIFY + M-SEARCH responses) + an HTTP server serving device/service description XML + SOAP control endpoints + GENA eventing. Per the UPnP MediaRenderer:1 device template, only RenderingControl and ConnectionManager are formally REQUIRED; AVTransport is optional in spec but mandatory in practice — VLC explicitly refuses renderers lacking AVTransport::SetAVTransportURI. A working minimal action surface (proven by Music Assistant's dlna-receiver plugin) is: AVTransport {SetAVTransportURI, Play, Pause, Stop, Seek, GetTransportInfo, GetPositionInfo, GetMediaInfo}, RenderingControl {Get/SetVolume, Get/SetMute}, ConnectionManager {GetProtocolInfo, GetCurrentConnectionIDs, GetCurrentConnectionInfo}, plus GENA SUBSCRIBE/NOTIFY with LastChange.

Best code to copy: gmrender-resurrect (C, GPL-2.0, active — pushed Feb 2026). Its src/ cleanly splits pure-UPnP files (upnp_device/upnp_service/upnp_transport/upnp_control/upnp_connmgr, webserver, variable-container for LastChange state) from playback via an output.h/output_module.h abstraction; only output_gstreamer.c is GStreamer-specific, so the whole UPnP side is portable if libupnp (pupnp) ports. pupnp itself is BSD-3, C, actively maintained (pushed Aug 2026), needs pthreads + BSD sockets, and has embedded tuning knobs (MAX_THREADS default 12, THREAD_STACK_SIZE). Alternatives: Platinum (C++, used by Kodi's UPnPRenderer.cpp), upmpdcli's pattern (UPnP front-end delegating playback to a separate player), and pschatzmann/arduino-dlna proving a renderer fits on an ESP32 without libupnp.

Sender compatibility: control points list renderers from NOTIFY/M-SEARCH responses carrying CACHE-CONTROL, EXT, LOCATION, SERVER, ST, USN; a root device sends ~3+2N+1 NOTIFYs and must honor MX delay. Biggest gotcha: senders filter by ConnectionManager protocolInfo — BubbleUPnP discards streams whose MIME isn't advertised and may substitute a different MIME in SetAVTransportURI; advertise a generous http-get:*:<mime>:* list. Web Video Caster notes most DLNA renderers can't play HLS. Even Kodi's renderer "sometimes refuses to show up" in controllers — discovery fragility is normal, plan for it.

Console prior art is thin, which is the finding: WiiMC (Wii) was neither a renderer nor even a UPnP client (SD/USB/DVD/SMB/FTP/HTTP only). No Switch, 3DS, Vita, or PSP homebrew UPnP renderer was found; NXMP (Switch) is a DLNA client, PSP tools are pull-based clients (PiMPStreamer) or screen mirrors (PSPdisp). The one true homebrew network receiver found is yellows8/ctr-streaming-server (3DS): custom TCP :8334, manual IP, no discovery, incomplete. XBMC on original Xbox had UPnP client (2006) + server (2007) and an HTTP API controllable from any browser — the canonical phone-browser-remote prior art; the renderer path exists in mainline Kodi via Platinum, unverified for XBMC4Xbox itself.

Fallback discovery: multicast SSDP/mDNS doesn't cross subnets and is often AP-blocked; manual-IP entry is the standard fallback (Home Assistant supports pinned Cast IPs). DIAL is simpler than UPnP AV but still SSDP-based, so it doesn't solve multicast loss. Directly relevant Wii U prior art: Ristretto, an Aroma WUPS plugin running an HTTP server on :8572 usable from any browser with Home Assistant/Homebridge integrations — proving the phone-browser/HTTP path works in Aroma. QR-encoding a local URL for phone pairing is common outside consoles; no console homebrew doing QR-to-phone-browser media control was found.

TOPIC: h264dec
----------------------------------------------------------------------------------------------------
SUMMARY:
Hardware H.264 decode on Wii U is a solved, well-trodden path for homebrew and is the correct primary strategy for WiiU Cast. wut ships complete headers for Nintendo's h264.rpl (include/h264/decode.h and stream.h): the flow is H264DECMemoryRequirement -> H264DECInitParam -> H264DECSetParam(_FPTR_OUTPUT/_OUTPUT_PER_FRAME/_USER_MEMORY) -> H264DECOpen -> H264DECBegin -> H264DECSetBitstream -> H264DECExecute -> Flush/End/Close, plus stream utilities (H264DECCheckDecunitLength, H264DECFindDecstartpoint, H264DECFindIdrpoint, H264DECGetImageSize). Limits (from the header plus the two independent emulator reimplementations, decaf and Cemu, which were reverse-engineered from the real library): profiles baseline(66)/main(77)/high(100) only, level up to 5.1, dimensions 64x64 (Cemu observes console checks ~32) up to 2800x1408 — so 1920x1080/1088 is within API limits. Work memory = 0x480000 base + per-level table (level 4.2 = 0x2200000, ~39MB total; level 5.1 = 0xB400000, ~189MB — likely impractical). Output is NV12 written into a caller-supplied buffer with row pitch = align_up(width,256), UV plane at y + pitch*alignedHeight; H264DecodeResult reports width/height/nextLine/crop/timestamp/VUI. H264DECExecute is synchronous; buffered mode delays output ~5 frames, OUTPUT_PER_FRAME=1 gives a frame per call (what moonlight uses for low latency). Real-world users: GaryOderNichts/moonlight-wiiu (users report 720p60 "almost flawless" over LAN adapter), cafemp media player (hardware h264 via an FFmpeg "h264_wiiu" codec built from GaryOderNichts/FFmpeg-wiiu; rewrote engine Oct 2025 "to support hardware decoding for h264 baseline 720p@30", enabled for all H.264 June 2026; actively developed as of Aug 2026), and mkwcat/magiquest-wiiu. wut itself has NO h264 sample; wiiubrew.org has NO H264.rpl page (empty); "Ristretto" is an IoT HTTP-server plugin, not a media player — but is relevant prior art for WiiU Cast's HTTP control plane. GX2 rendering: the proven zero-copy path (moonlight) is to decode directly into a GX2 texture data buffer and sample two linear textures — Y as GX2_SURFACE_FORMAT_UNORM_R8, UV as UNORM_R8_G8 — with a tiny YUV->RGB pixel shader (assembly shader in moonlight; precompiled GLSL .gsh in cafemp). A native GX2_SURFACE_FORMAT_UNORM_NV12 enum exists but no homebrew demonstrably samples it directly (magiquest only uses it to compute buffer size, then converts NV12->RGBA on CPU). Software decode ceiling: Wii precedent (WiiMC on 729MHz PPC750) managed H.264 only to 720x480, MPEG-4 ASP to 656x352, MPEG-2 PS to 720x480, MPEG-2 TS to 1280x720, and explicitly could not decode 720p/1080p H.264. Espresso is 3x PPC750-class cores at 1.243GHz with paired-singles only (no AltiVec), so software H.264 realistically tops out around 480p-576p reliably; cafemp's multithreaded software FFmpeg claimed "maybe 720p30" but moved to hardware decode, implying software 720p was marginal. MPEG-4 ASP/MPEG-2 at SD-to-720p and VP8 at ~480p are plausible fallbacks (inference; no Wii U measurements found). Audio: software decode is comfortably feasible — moonlight decodes 48kHz multistream Opus in software, magiquest decodes Ogg Opus via opusfile on a dedicated thread, cafemp decodes AAC/MP3/etc. via FFmpeg on a thread, and even the Wii played AAC/AC3/FLAC/MP3/Vorbis fine.

VERDICTS:
  ### sw-decode: CONFIRMED
      Both halves of the claim check out against primary sources, with one epistemic caveat.

CPU facts: WiiUBrew's Hardware page states Espresso is an "IBM PowerPC based processor... Clocked at 1243.125 MHz. Three Cores (nicknamed CPU0, CPU1, CPU2), each with one thread." fail0verflow (marcan, who dumped the Espresso via the boot ROM) confirms it is PPC750-family (it must be Broadway-compatible to run Wii software) and that "the PPC750 line is the only range of PowerPC processors that implement Paired Singles... not compatible with modern PowerPC SIMD, such as AltiVec." So "3x PPC750 @1.24GHz, no AltiVec" is accurate. Nuance: it does have Gekko-style paired-singles (2-wide float SIMD), which is essentially useless for integer-dominated H.264 decoding, so the practical point stands.

Software decode infeasibility: I actively searched for a counter-example (any homebrew doing real-time HD H.264 in software) and found none. All primary evidence points the other way: (1) moonlight-wiiu's decode.c uses the wut H264DEC API exclusively, and maintainer GaryOderNichts' release announcement states "It's using the hardware-accelerated h264 library of the Wii U which results in pretty fast decoding. Using a LAN Adapter 720p@60fps runs almost flawlessly." (2) GaryOderNichts maintains an entire FFmpeg fork (FFmpeg-wiiu) whose sole purpose is adding libavcodec/h264_wiiu.c — "H.264 Decoder using h264.rpl" — wrapping H264DECInitParam/Open/Begin/SetBitstream/Execute; nobody builds a hardware wrapper into FFmpeg if FFmpeg's own software decoder suffices. (3) cafemp, the current Wii U media player, selects avcodec_find_decoder_by_name("h264_wiiu") for H.264 and uses software decoding (thread_count=2) only for other codecs; even WITH the hardware decoder its README calls 720p30 "the goal, not a guarantee." (4) A GBAtemp post states verbatim: "The Wii U supports h264 hardware decoding only and the CPU is too slow to software decode anything serious" (poster identity unverifiable — page returns 403 — but the quote's existence was verified via search). (5) Corroborating scale: wut contributor ashquarky's MJPEGOnWiiU shows even 720p MJPEG — vastly cheaper than H.264 — ran at well under half real time in software (a 30s clip took ~70s; 5-6M ticks/frame). (6) Same-microarchitecture baseline: WiiMC on the Wii's single 729MHz Broadway (same PPC750 core) topped out around 480p H.264 with 720p unplayable; Espresso is ~1.7x the clock with 3 such cores, far short of the ~5-10x needed for reliable 720p, let alone 1080p.

Caveats/nuance: (a) "Cannot reach HD in real time" is a unanimous, well-evidenced engineering consensus among the people who actually shipped Wii U video homebrew, but no rigorously published benchmark of an optimized software 720p decode exists — a highly tuned CAVLC/baseline 720p24 low-bitrate edge case has never been demonstrated but also never formally disproven. Practical software ceiling is ~SD/480p. (b) The claim's "required for 720p and above" slightly understates reality: homebrew uses H264DEC at ALL resolutions (moonlight uses it even at 854x480) because it is faster and frees the CPU; hardware is not merely a >=720p fallback. (c) The hardware decoder's envelope does cover HD as claimed: h264.rpl accepts up to 2800x1408, level <=5.1, baseline/main/high profiles only — so 1080p is within hardware scope but e.g. 4K or non-BP/MP/HP streams are not. (d) The exact silicon block behind h264.rpl (UVD-like unit in the R7xx-derived Latte) is not publicly documented on WiiUBrew; "hardware-accelerated" rests on maintainer statements plus the performance delta (720p60 near-flawless via H264DEC vs. sub-real-time 720p MJPEG on CPU), which is conclusive for the feasibility question regardless of which die block does the work.

  ### hw-decoder: CONFIRMED
      Three of the four components are solidly confirmed by primary sources; the fourth ("limited to roughly Level 4.1, max 1080p") is directionally right for practical purposes but wrong as stated — the real envelope is larger. (1) API exposure: raw wut master headers (devkitPro/wut include/h264/decode.h and stream.h) declare the complete API exactly as described: H264DECMemoryRequirement(profile, level, maxWidth, maxHeight, out), H264DECInitParam, H264DECSetParam + typed variants _FPTR_OUTPUT/_OUTPUT_PER_FRAME/_USER_MEMORY, H264DECCheckMemSegmentation, H264DECOpen/Begin/SetBitstream(buffer, length, double timestamp)/Execute(memory, frameBuffer)/Flush/End/Close, plus stream helpers H264DECCheckDecunitLength, H264DECCheckSkipableFrame, H264DECFindDecstartpoint, H264DECFindIdrpoint, H264DECGetImageSize. (2) NV12 output: confirmed by three independent codebases — GaryOderNichts' FFmpeg-wiiu h264_wiiu.c states verbatim that the Wii U decoder only outputs NV12 and copies with AV_PIX_FMT_NV12, pitch=(width+255)&~255, UV plane at framebuffer+height*pitch; decaf-emu's h264_decode_ffmpeg.cpp emulates the real library with AV_PIX_FMT_NV12, pitch=align_up(width,256), decodeResult->nextLine=pitch, crop fields populated; moonlight-wiiu renders the planes as GX2 R8 (Y) + R8G8 (UV) textures with H264_FRAME_PITCH ((w+0xff)&~0xff). Caveat: the wut header itself never names the pixel format — NV12 is established by implementations, not official docs. (3) CORRECTION on limits: the claim's "roughly Level 4.1 (max 1080p)" understates the decoder. Both reverse-engineered reimplementations of the real h264.rpl agree the library validates: profiles baseline(66)/main(77)/high(100) only (also stated in wut stream.h's H264_ERROR_INVALID_PROFILE comment); resolution 64x64 (Cemu implements <32 rejection) up to 2800x1408 maximum; level rejected only at >=52, i.e. the API accepts up to Level 5.1 (decaf: MaximumWidth=2800, MaximumHeight=1408, level>51 -> InvalidParameter; Cemu: width>2800||height>1408||codecLevel>=52 -> INVALID_PARAM). The oft-quoted "maximum supported level (level 42)" originates from GaryOderNichts' FFmpeg-wiiu commit 24997bd (Dec 2020), whose comment hardcodes the level-4.2 work-memory size (0x2200000+0x3ff+0x480000 ~= 40MB; decaf's table: level 41=0x2000000, 42=0x2200000, 50=0x6BD0000 ~113MB, 51=0xB400000 ~189MB, base 0x480000) — that comment was copied into moonlight-wiiu. So "4.1" is wrong under either reading (hardware author says 4.2; API validation says 5.1), and "max 1080p" is wrong as a hard limit (2800x1408 accepted) — but the load-bearing conclusion for a feasibility audit holds a fortiori: 1080p (1920x1088 coded) is comfortably inside the decoder's envelope. (4) Real homebrew: moonlight-wiiu (game-streaming client, seven releases wiiu-v1.0 Mar 2021 through wiiu-v1.6 Feb 2024) drives the full H264DEC sequence with H264DECSetParam_OUTPUT_PER_FRAME(decoder, 1) for per-call frame output, and FFmpeg-wiiu integrates h264.rpl as an FFmpeg decoder the same way; Cemu's code comments corroborate that H264DECExecute is synchronous, emitting a frame every call in non-buffered mode or after ~6 calls (5-frame internal buffer) in buffered mode. Remaining caveats: the level/resolution limits come from reverse-engineered emulator code, not an official Nintendo spec (wut documents no limits at all); and whether the physical decoder can sustain real-time decode at the extreme 2800x1408/L5.1 corner is unproven — homebrew authors allocate for level 4.2 and stream at 720p-1080p in practice.

DECISIVE QUESTION (multicast RX): The Wii U socket stack (nsysnet, IOSU-side) does support IPv4 UDP multicast including IP_ADD_MEMBERSHIP. wut PR #331 (GaryOderNichts, merged 2023-10-17, shipped in wut v1.4.0) added IP_MULTICAST_IF/TTL/LOOP, IP_ADD_MEMBERSHIP(=12)/IP_DROP_MEMBERSHIP(=13), struct ip_mreq, and the nsysnet export set_multicast_state(BOOL); the PR states these optnames are "supported on the IOSU-side implementation, which includes support for multicast" and that set_multicast_state(TRUE) is required or bind/sendto to multicast addresses fail with ENETUNREACH. wut now calls set_multicast_state(TRUE) automatically in __init_wut_socket, so every wut app gets it. Practical evidence: ftpiiu_plugin (Maschell) shipped mtheall/ftpd's mDNS responder ENABLED on Wii U in v0.4.4 (Feb 2025) and disabled it in v0.4.5 (PR #81, Feb 2026) — explicitly because of plugin-heap memory pressure (64KiB periodic allocations), NOT because multicast failed. AorsiniYT/mdnsniff (May 2026) implements a working-styled mDNS receiver for Wii U (bind 5353, SO_REUSEADDR, SO_RCVBUF, IP_ADD_MEMBERSHIP join of 224.0.0.251). Counter-signal: lovepotion stubs all multicast setsockopts on __WIIU__. No public report positively confirms received SSDP datagrams on 239.255.255.250; a hardware spike test is the top recommendation. SO_BROADCAST (0x0020) exists; broadcast SEND is routine (UDP logging to port 4405); no broadcast-RECEIVE precedent found.

DISCOVERY TODAY: moonlight-wiiu uses MANUAL IP entry in moonlight.conf — no mDNS/SSDP. No Wii U DLNA/UPnP receiver homebrew exists; wiiu-smarthome lists SSDP/UPnP as "future possible subprojects". Nothing from Pretendo. Closest mdns-lib lead: AorsiniYT's fork of mjansson/mdns.

SOCKET QUIRKS: nsysnet exports select (NOT poll); wut emulates poll() over select with NSYSNET_FD_SETSIZE=32 fd cap. Nonblocking via SO_NBIO/SO_BIO/SO_NONBLOCK (InterNiche-style options). Throughput tuning is mandatory: somemopt (nn/nets2) donates a 0x40-aligned user buffer (min 128KiB, max 3MiB, blocking init on its own thread) to the stack; SO_RUSRBUF(0x10000) enables it per-socket; SO_WINSCALE, SO_NOSLOWSTART exist. moonlight-wiiu and RetroArch both use somemopt at the 3MiB max. HTTP/FTP server precedents: Ristretto (Aroma WUPS plugin, modified kissbeni/tinyhttp, port 8572, active 2026) — documents that servers stop responding when a system applet/HOME menu puts the process in background, and had a bug allocating all memory on network drop; ftpiiu_plugin (ftpd-based, poll()-driven multi-connection FTP, active); wiiload plugin (persistent TCP listener); Laf111/WiiuFtpServer (8 simultaneous transfers, stale 2022).

PHYSICAL LAYER: Console internet Wi-Fi is 2.4GHz-only 802.11b/g/n (Nintendo official; 5GHz-only routers incompatible); Broadcom BCM43362/43237/4319 handle Wi-Fi with 5GHz reserved for the GamePad link. Official Wii LAN Adapter (USB, 10/100) is Nintendo-supported on Wii U and transparent to homebrew (moonlight README: "A Wii U LAN Adapter is recommended!"). Reported real-world FTP speeds: ~120KB/s (old ftpiiu), 0.8–1MB/s typical, ~3.5MB/s (28Mbps) with WiiuFtpServer + LAN adapter. moonlight-wiiu troubleshooting suggests starting at 1.5Mbps/480p30 and increasing. Safe planning envelope: ~5–10Mbps sustained over Wi-Fi, ~25–30Mbps over LAN adapter — enough for 720p H.264 at moderate bitrates, marginal for high-bitrate 1080p over Wi-Fi.

SUMMARY:
The graphics/UI/audio stack for WiiU Cast is in better shape than typical console homebrew. The SDL2 Wii U port's canonical home in 2026 is devkitPro/SDL, branches wiiu-sdl2-2.28 and wiiu-sdl2-2.32 (SDL 2.32.7 in-tree; shipped as official devkitPro pacman package wiiu-sdl2 2.32.10-2 with SDL2_gfx/image/mixer/net/ttf companions). It is actively maintained — commits Feb 2026 by GaryOderNichts and Daniel K. O. The older forks (yawut/SDL, formerly rw-r-r-0644/SDL, last push Sep 2024; GaryOderNichts/SDL_mirror, last push Mar 2021) are historical. Wii U support was never upstreamed to libsdl-org/SDL.

Dual screen: the port registers TWO SDL displays (TV up to 1080p, DRC fixed 854x480) and defines three Wii U-specific window flags in SDL_video.h: SDL_WINDOW_WIIU_GAMEPAD_ONLY (0x01000000), SDL_WINDOW_WIIU_TV_ONLY (0x02000000), SDL_WINDOW_WIIU_PREVENT_SWAP (0x04000000). Default behavior is mirroring — the present path copies the window's color buffer to BOTH GX2 scan targets — but independent TV/GamePad content is explicitly supported via two windows with TV_ONLY/GAMEPAD_ONLY flags (PREVENT_SWAP coordinates the double present). In raw GX2, independent rendering is standard: wut's WHBGfx allocates separate double-buffered TV/DRC scan buffers (GX2SetTVBuffer/GX2SetDRCBuffer) and a separate GX2ContextState per screen; moonlight-wiiu draws distinct passes via WHBGfxBeginRenderTV/WHBGfxBeginRenderDRC.

OSScreen is fine for a phase-0 text UI: double-buffered software framebuffers for both screens, RGBX8 big-endian, built-in monospace font at character-grid positions, but only per-pixel plotting otherwise — no blits, images, or alpha.

Audio: SDL's Wii U backend sits on AX/sndcore2 — AXInit at AX_INIT_RENDERER_48KHZ (48 kHz hardcoded), S16MSB forced, one looping AX voice per channel, output mixed to both TV and DRC speakers via AXSetVoiceDeviceMix, driven by a 3 ms AXRegisterAppFrameCallback pinned to CPU1. moonlight-wiiu proves streamed audio works through plain SDL_OpenAudioDevice/SDL_QueueAudio with CPU-side Opus decode.

GamePad screen power: VPADSetLcdMode/VPADGetLcdMode (wut vpad/input.h) with VPAD_LCD_STANDBY=0, VPAD_LCD_OFF=1, VPAD_LCD_ON=0xFF; the Padcon plugin demonstrates toggling off/on with VPADSetLcdMode(0,1)/(0,0xFF).

Video presentation: moonlight-wiiu is the blueprint. The system H264DEC library decodes H.264 DIRECTLY into GX2 texture memory as NV12 — Y plane as GX2_SURFACE_FORMAT_UNORM_R8, interleaved UV as UNORM_R8_G8 at half res, GX2_TILE_MODE_LINEAR_ALIGNED, pitch 256-aligned — zero CPU upload; a GFD pixel shader does YUV→RGB while drawing a fullscreen quad to both screens. Decoder work memory is ~34 MB (level 4.2 max). Important caveats: the SDL2 GX2 renderer exposes 15 RGB(A) texture formats and NO YUV formats, so NV12 via SDL_Texture is not available — WiiU Cast needs the raw-GX2 shader path (or CPU NV12→RGBA conversion). Ristretto (wiiu-smarthome/Ristretto) is NOT a media app — it's an Aroma WUPS plugin exposing an HTTP smart-home API; useless as a video-presentation example, though relevant as prior art for an HTTP control server on Wii U.

(3) src/video/wiiu/SDL_wiiuvideo.c registers two SDL displays (TV at 854x480/1280x720/1920x1080 and DRC at 854x480) and iterates a window list, and src/render/wiiu/SDL_render_wiiu.c allocates a per-renderer GX2ContextState and per-window color buffer, so multiple windows/renderers coexist. (4) Decisive real-world proof: the homebrew Uxplore (Kuruyia/Uxplore, source/Application.cpp) creates exactly two windows — one SDL_WINDOW_WIIU_TV_ONLY and one SDL_WINDOW_WIIU_GAMEPAD_ONLY — each with its own SDL_RENDERER_ACCELERATED renderer, draws different content to each (renderSecondary on the GamePad renderer), and calls SDL_RenderPresent on both every frame. GitHub code search shows several other projects using the flag (Unitendo/aurorachat-wiiu, Eitan1414 FNaF3 Wii U, PinkQween/CVN). The flags are also present in the SDL2-2.32.10.patch inside devkitPro/wut-packages, so the shipped wiiu-sdl2 pacman package includes this capability. Nuances/corrections to the researcher's context: (a) the two-window pattern is not mere inference — Uxplore demonstrates it in shipping code; (b) SDL_WINDOW_WIIU_PREVENT_SWAP is NOT required for the pattern to work — Uxplore presents both windows per frame without it (GX2SwapScanBuffers swaps TV and DRC scan buffers together, and both copies happen before the swap); the flag is an optional optimization to avoid a redundant second swap; (c) this is entirely port-specific API — no upstream libsdl-org/SDL Wii U backend exists and no SDL3 port, so code using these flags is non-portable and must be guarded for Wii U builds; (d) default behavior with a single plain window is mirroring the same content to both screens.

CRITIQUE
====================================================================================================
GAPS:
  - SSDP multicast RX spike never executed: the audit's decisive unknown (does IP_ADD_MEMBERSHIP on 239.255.255.250:1900 deliver datagrams on real hardware, does IOSU emit IGMP reports, does 2.4GHz power-save drop multicast) is answerable with a ~50-line .wuhb test in an afternoon — it must be Phase 0 and gates the entire discovery architecture (SSDP vs manual-IP/QR/HTTP fallback).
  - Arbitrary-file decode is unproven: every working H264DEC consumer (moonlight, magiquest) feeds B-frame-free Annex-B low-latency streams. Cast targets are ordinary MP4/MKV with B-frames and AVCC framing. Buffered mode (5-6 frame delay) + timestamp reordering + AVCC-to-Annex-B conversion is untested; this is closer to go/no-go than the researchers treated it, since it decides whether typical phone videos play at all.
  - Throughput-vs-bitrate math is unresolved and rests on unverified numbers: Wi-Fi envelope (~5-10 Mbps) vs typical phone-video bitrates (10-40 Mbps) implies most 1080p files fail over Wi-Fi; the FTP throughput figures come from unreadable GBAtemp pages (403). No direct HTTP-GET streaming benchmark on hardware exists, and no product decision is recorded (require LAN adapter? sender-side transcode? cap at 720p?).
  - HTTPS/TLS entirely unexamined: many real sender apps hand out https:// URLs and redirects. mbedtls/curl portlibs exist (moonlight links them) but TLS handshake behavior, cert store, SNI, and Espresso CPU cost of decrypting a 10-20 Mbps TLS stream while video decodes were never researched.
  - HLS is a named risk with no plan: the researchers cite Web Video Caster's warning that most DLNA renderers can't play HLS, yet a large share of real casting attempts (web video) are HLS. In/out-of-scope decision needed — it drives whether FFmpeg avformat (TS demux, playlist handling, discontinuities) is a hard dependency.
  - License compatibility matrix never assembled: gmrender-resurrect is GPL-2.0 and moonlight-wiiu is GPL-3.0 — if gmrender is GPLv2-only these cannot be combined in one binary; CaféMP has no license at all; FFmpeg is LGPL/GPL mixed. This decides copy-vs-reimplement for both the UPnP layer and the player core, i.e., the effort estimate.
  - No consolidated memory budget: H264DEC work memory (~39MB at L4.2, ~189MB at L5.1 called 'likely impractical' without saying why), somemopt 3MiB, pupnp thread stacks, FFmpeg demux buffers, GX2 scan buffers — never summed against the actual application memory available to a .wuhb under Aroma (which the dossier never states). Determines whether L5.1/1080p allocation and pupnp's 12-thread pool are even possible.
  - Level 4.2 vs 5.1 contradiction unresolved plus zero real-time 1080p decode measurement: moonlight's author says 4.2 max, decaf/Cemu accept 5.1. Bounds the advertised quality ceiling; needs the H264DECMemoryRequirement(level=51) + 1080p hardware test the researchers themselves proposed.
  - CPU headroom during playback unknown: whether h264.rpl runs on dedicated Latte silicon or burns CPU determines if demux + software audio decode + HTTP serving + UPnP GENA eventing fit on 3 Espresso cores at 1080p — no measurement or even estimate exists.
  - A/V sync end-to-end has no verdict: audio master clock (cafemp pattern) + hardware decode's 5-frame buffered-mode latency + network jitter is a different problem from moonlight's low-latency mode; cafemp's own seek-freeze and crash bugs suggest fragility. No sync design was selected.
  - Seek path undesigned: DLNA Seek action -> HTTP Range request support in the chosen client -> H264DECFlush -> IDR reacquisition (H264DECFindIdrpoint) is a chain nobody analyzed; seek is table stakes for senders' progress bars.
  - Subtitles never mentioned in any topic: embedded SRT/ASS in MKV, DLNA captioning, and libass feasibility on Espresso are absent — a scope decision that affects demuxer choice and phase ordering.
  - Sender-UX reality unstated: Android/iOS native cast buttons are Chromecast/AirPlay, not DLNA — users must install a third-party app (BubbleUPnP, Web Video Caster, LocalCast). No sender test matrix, no empirical protocolInfo/GENA requirements (flagged open for Web Video Caster/LocalCast), and no statement of this UX limitation in the product premise.
  - Always-on-receiver vs console power management: Ristretto proves the server dies under Home menu/applets (flagged), but nobody asked whether the app can suppress auto power-down (IM/APD APIs) or what idle-waiting does to TV/GamePad screens — core to a device whose job is to sit waiting for a cast.
  - The app-vs-plugin architecture question (single .wuhb with server vs Ristretto-style plugin + app launch) is flagged twice but has no recommendation, despite dictating the repo structure from day one.
  - Distribution/legal risk unaddressed: 'WiiU' trademark in the product name, hb-appstore listing requirements, Nintendo's posture toward network-facing homebrew — low technical risk but belongs in a feasibility audit.
  - The av-stack topic's open-questions list is truncated in the dossier itself (cuts off mid-item on the SDL two-window spike), and several load-bearing performance anecdotes (Moonlight 720p60, FTP speeds) trace to Cloudflare-blocked GBAtemp threads — the record needs manual re-verification before the audit cites them.
  - Prior-art topics carry empty verdicts arrays: no claim in prior-art-wiiu or prior-art-cross was formally verified, unlike h264dec and network — inconsistent evidence standard across the audit.

GO/NO-GO FACTORS:
  - Core pipeline (network in -> hardware H.264 decode -> NV12 -> GX2 TV/GamePad out): CONFIRMED VIABLE. Moonlight Wii U proves it end-to-end at 720p60 (LAN); both h264dec verdicts CONFIRMED; zero-copy decode-into-texture path documented and reusable (GPL-3.0).
  - SSDP multicast reception (what makes it a discoverable cast receiver rather than a manual-IP app): UNKNOWN (audit verdict UNCERTAIN). API present and auto-enabled since wut v1.4.0, strong indirect mDNS evidence, but no positive receive report on 239.255.255.250 and IGMP-snooping/Wi-Fi power-save behavior untested. A one-afternoon hardware spike settles it; manual-IP/QR/HTTP fallback exists but weakens the premise.
  - Decoding ordinary cast files (B-frames, AVCC MP4/MKV containers, buffered-mode reordering): UNKNOWN. All proven H264DEC usage is B-frame-free streaming; typical phone/library files are not. If buffered mode + reordering fails or stutters, the product's main use case fails regardless of everything else — needs an early hardware spike ranked equal to the SSDP test.
  - Network throughput vs real media bitrates: PARTIAL BLOCKER (Wi-Fi) / CONFIRMED VIABLE (LAN adapter). ~5-10 Mbps sustained Wi-Fi vs 10-40 Mbps typical files means high-bitrate 1080p over Wi-Fi likely fails; ~25-30 Mbps via LAN adapter suffices. Underlying figures unverified (GBAtemp blocked) and no direct HTTP streaming benchmark exists.
  - UPnP/DLNA renderer stack on wut sockets (pupnp port or hand-rolled SSDP+SOAP+GENA): UNKNOWN, leaning viable. Minimal required action surface fully documented (Music Assistant reference), Aroma HTTP-server precedent confirmed (Ristretto), gmrender architecture cleanly separable — but pupnp's thread-pool/32-fd-select fit and GENA depth needed by real senders are unverified.
  - Sender-app acceptance (protocolInfo filtering, GENA subscription requirements, discovery fragility, HLS refusal): UNKNOWN. BubbleUPnP MIME filtering documented; Web Video Caster/LocalCast requirements unmeasured; even Kodi's renderer sometimes fails to appear. Requires packet-capture testing against a prototype — cannot be resolved from research alone.
  - HTTPS media fetching: UNKNOWN — never researched. mbedtls/curl portlibs exist (moonlight precedent) but TLS-at-streaming-bitrate CPU cost and cert handling on Wii U are unmeasured; many sender apps only produce https URLs, so a failure here silently kills large sender coverage.
  - Audio decode and A/V sync: components CONFIRMED VIABLE (software Opus/AAC/MP3 decode proven by moonlight/cafemp/magiquest; AX/SDL2 audio path solid), end-to-end sync under network jitter with 5-frame buffered video decode UNKNOWN.
  - 1080p ceiling: UNKNOWN (720p CONFIRMED VIABLE). Level 4.2-vs-5.1 contradiction and absent real-time 1080p throughput measurement leave max quality unbounded; not fatal if the product ships as a 720p-class receiver.
  - Toolchain and AV presentation stack (devkitPro SDL2 fork active, dual-screen GX2, NV12 shader path, VPAD LCD control): CONFIRMED VIABLE, with the known caveat that SDL's renderer has no YUV textures so video must use the raw-GX2 shader path.
  - Always-on receiver vs Cafe OS constraints: CONFIRMED CONSTRAINT with unknown mitigation — servers stop under Home menu/applets (Ristretto), auto power-down and idle-screen behavior unexamined; shapes architecture (app vs plugin split) rather than blocking outright.
  - Code-reuse legality: UNKNOWN/DECISION PENDING. GPL-2.0 (gmrender) + GPL-3.0 (moonlight) may be incompatible in one binary; CaféMP is unlicensed. Doesn't block feasibility but swings the effort estimate between 'assemble proven parts' and 'reimplement'.
  - Niche emptiness and demand-side risk: CONFIRMED empty (no DLNA/AirPlay/Chromecast receiver exists on any Nintendo console) — but note the flip side is unvalidated demand and a sender UX that requires users to install third-party casting apps.
